# Basin Pipelines and Basin SQL limitations

Verified October 14, 2026 against Cloudflare's documentation source at [`d7ed1c16003f1fdc41f1a493572150a03f208111`](https://github.com/cloudflare/cloudflare-docs/tree/d7ed1c16003f1fdc41f1a493572150a03f208111). Direct documentation pages were inaccessible from this environment; current official Git sources were available. These are documented capabilities and limits, not live-account benchmarks or experiments.

## Basin Pipelines

Pipelines is a continuous **stream → stateless SQL → sink** service. It is useful for managed ingestion, filtering, reshaping, computed fields, and event routing. It is not currently documented as a general stateful stream processor or a batch transformation engine. [Product overview](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/index.mdx), [stateless transform scope](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/platform/pricing.mdx)

| Limitation                                                                                                                                                        | Practical consequence                                                                                                                                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stream input, rather than arbitrary catalog reads.** Documented statements are `INSERT INTO sink SELECT ... FROM stream`; `FROM` also supports CTEs/subqueries. | A pipeline does not automatically execute a dbt model's compiled query over persisted tables. Multiple statements support fan-out to several sinks.                                                                  |
| **Stateless transforms.** Current scope is filter, reshape, unnest, cast, compute. Stateful aggregations, joins, and windows are described as future operations.  | Rolling aggregates, stream joins, and stateful deduplication need another mechanism. `UNNEST` is restricted to the SELECT clause and one array per SELECT.                                                           |
| **No documented row mutation/CDC mode.** No native upsert, merge, update, row-delete, primary-key reconciliation, or CDC-envelope application contract was found. | Ingesting a record with `operation='delete'` stores a change event; it does not establish deletion of an existing row. Iceberg can support mutations through compatible external writers, separately from Pipelines. |
| **Stream schema, pipeline SQL, and sink configuration cannot be edited after creation.**                                                                          | Changes require replacement and a planned cutover. HTTP-ingest authentication/CORS settings can be changed. Deleting a stream loses unprocessed buffered events and dependent pipelines.                             |
| **New Catalog sinks cannot target existing Iceberg tables.**                                                                                                      | Existing-table adoption and sink replacement cannot assume arbitrary reattachment. Catalog sinks output Parquet only and require Catalog plus storage write access.                                                  |
| **Batched visibility.** Catalog sink rolling interval: minimum 60 seconds, default 300. Raw R2 sink interval: minimum 10 seconds, default 300.                    | Ingestion acknowledgement is not instant query visibility. These are configurable rolling intervals, not end-to-end freshness guarantees.                                                                            |
| **Jurisdiction restriction.** Basin Catalog currently supports only the default R2 jurisdiction.                                                                  | Do not promise an EU-jurisdiction Catalog sink. This is narrower than saying Cloudflare has no geographic data controls generally.                                                                                   |
| **Malformed events can be accepted, then dropped.**                                                                                                               | Validate producers and monitor decode/user-error metrics; successful ingestion alone does not establish complete sink delivery.                                                                                      |

Sources: [SQL statement scope and UNNEST](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/sql-reference/select-statements.mdx), [pipeline immutability](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/pipelines/manage-pipelines.mdx), [stream schema and deletion](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/streams/manage-streams.mdx), [sink immutability](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/sinks/manage-sinks.mdx), [Catalog sink](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/sinks/available-sinks/r2-data-catalog.mdx), [raw R2 sink](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/sinks/available-sinks/r2.mdx), [Catalog jurisdiction](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-catalog/manage-catalogs.mdx#L379), [ingest acknowledgement and invalid events](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/streams/writing-to-streams.mdx).

### Published quotas

Pipelines requires Workers Paid. Current default limits are **20 streams, 20 pipelines, and 20 sinks per account**, **5 MB per ingestion request**, and **1 GB/s maximum ingest rate per stream**. Quotas are shared across projects in the account. Cloudflare links a limit-increase process; the documented rate is not a measured throughput guarantee. [Current limits](https://developers.cloudflare.com/basin-pipelines/platform/limits/), [pinned source](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/platform/limits.mdx)

### Guarantees and remaining unknowns

Cloudflare documents exactly-once **sink delivery**. The inspected docs do not define application-event-ID deduplication across producer resubmissions, user-controlled historical replay/offsets, a stream retention period, or replay behavior after replacing pipeline SQL. These are unestablished contracts, rather than empirically rejected features. Preserve source IDs/positions and verify retry/replay behavior before promising CDC correctness or lossless backfills. [Delivery guarantee](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/sinks/index.mdx), [stream description](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-pipelines/streams/index.mdx)

One documentation inconsistency remains: the end-to-end tutorial configures a 30-second Catalog roll interval, while the dedicated sink reference states a 60-second minimum. Use the dedicated reference for planning and confirm actual validation in an account. [Conflicting tutorial](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/tutorials/end-to-end-pipeline.mdx#L254)

## Basin SQL

Basin SQL runs analytical queries over Parquet data in Basin Catalog-managed Iceberg tables. Its query feature set is substantial, but its read-only boundary is explicit. It is not a BigQuery/Snowflake-style SQL endpoint for both transformation and persisted materialization. [Product overview](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/index.mdx), [support matrix](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/reference/limitations-best-practices.mdx)

| Limitation                                                                                                                                                                                                                                                  | Practical consequence                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Read-only.** No `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, or `ALTER`.                                                                                                                                                                               | `SELECT ... GROUP BY` can compute a result, but `CREATE TABLE AS SELECT` cannot persist it. Ordinary dbt table/view creation, merge, full refresh, and SQL-based schema migration require a different write path. |
| **Parquet data only, through Catalog-managed Iceberg tables.**                                                                                                                                                                                              | Raw CSV/JSON files in R2 are not directly queryable through this interface. JSON-valued columns/functions are a separate question from file-format support.                                                       |
| **Dialect gaps.** No `OFFSET`, `UNNEST`, `PIVOT`/`UNPIVOT`, named `WINDOW` clause, lateral derived tables, nested parenthesized joins, or documented wildcard exclusion/replacement modifiers.                                                              | Existing warehouse SQL needs compatibility checks. Pipeline UNNEST support does not imply Basin SQL UNNEST support.                                                                                               |
| **Result bounds.** SQL reference documents a default `LIMIT` of 500; troubleshooting documents an allowed range of 1–10,000.                                                                                                                                | Plan bounded previews and exports. Pagination needs stable key-based ordering/filtering rather than OFFSET; this is distinct from a scan-volume limit.                                                            |
| **Memory/compute constraints.** Large joins, high-cardinality aggregates, exact distinct aggregates, large sorts, and wide window partitions can time out. Some expensive functions are budget-gated and can be rejected with a 400 error before execution. | Supported syntax is not a guarantee of execution at arbitrary scale. Filter and prune data; benchmark representative workloads before choosing production SLAs.                                                   |
| **Expression details.** `NOT IN` subqueries on nullable columns are unsupported; named windows are unsupported but inline `OVER (...)` works.                                                                                                               | Use `NOT EXISTS` where appropriate and validate semantics as well as syntax.                                                                                                                                      |

Sources: [Current support and resource constraints](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/reference/limitations-best-practices.mdx), [SQL reference and default LIMIT](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/sql-reference/index.mdx#L607), [maximum LIMIT and pagination](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/troubleshooting.mdx#L163).

The current support matrix explicitly includes CTEs, standard joins, scalar/derived/EXISTS subqueries, aggregates, inline window functions, QUALIFY, DISTINCT, set operations, and GROUPING SETS/ROLLUP/CUBE. Describing Basin SQL as unable to join or aggregate would be inaccurate. Window functions, DISTINCT aggregates, MEDIAN, percentile operations and array/string aggregation have documented budget qualifications; a latest-per-key CDC query may therefore work logically but still need performance validation. [Supported features and budgets](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/reference/limitations-best-practices.mdx)

Current pricing meters compressed bytes scanned: 10 GB/month included, then $0.0025/GB, with a 10 MB minimum per query. Standard R2 reads/storage and Catalog operations are additional dimensions. Limiting returned rows does not itself establish a low scan cost. [Pricing](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/platform/pricing.mdx)

The query-auth example asks for write-oriented R2 scopes, while the Catalog guide describes read-only storage/catalog access for readers. Resolve least-privilege behavior in a real account before shipping role presets. The troubleshooting page also includes older JSON-function statements that do not align cleanly with the current support matrix; use the specific current function reference and verify needed expressions rather than inferring a blanket JSON prohibition. These are documentation qualifications, not reproduced runtime failures. [Query authentication](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/query-data.mdx#L67), [Catalog permissions](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-catalog/manage-catalogs.mdx#L279), [JSON function reference](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/sql-reference/scalar-functions.mdx), [troubleshooting](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-sql/troubleshooting.mdx).

## What this means for the two projects

For Dagflare, streaming assets need observed watermarks, decode/drop metrics, schema checks, and explicit migration/cutover plans. Batch-derived assets need a separate finite execution and verified commit path. Neither acknowledgement nor a configured pipeline is proof of a usable dataset.

For standalone `dbt-cloudflare-basin`, Pipeline stream transforms do not directly replace compiled dbt queries over stored relations. Basin SQL can execute compatible read queries, but cannot perform ordinary dbt materializations. Evaluate the existing upstream dbt v2/DuckDB Iceberg path and engine-specific limitations; do not infer generic merge/delete support from the fact that the data resides in Iceberg. [Existing dbt integration evidence](dbt-basin-existing-work.md)

Cloudflare documents row deletion through an Iceberg-compatible engine such as Spark, using transactional Catalog commits. That establishes a separate mutation path, not row-delete support in Pipelines or Basin SQL. Logical deletion and eventual removal of retained snapshots/data files are also separate operations. [Catalog deletion](https://github.com/cloudflare/cloudflare-docs/blob/d7ed1c16003f1fdc41f1a493572150a03f208111/src/content/docs/basin-catalog/deleting-data.mdx)
