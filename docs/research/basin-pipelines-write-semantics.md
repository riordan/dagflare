# Basin Pipelines writes and the two project scopes

Research date: October 13, 2026. Sources inspected: Cloudflare documentation at `f00bec2e4a282dce209c83ce5ad43001706ee2fb` and its generated TypeScript SDK at `6dbe1fc45b41f102e5edcd3630d6fd3e803552ce`.

**Basin Pipelines should be a core Dagflare primitive.** They provide managed continuous ingestion, stateless transformations, routing, and Iceberg-table delivery. The documented write path is stream-to-sink insertion. We found no documented native row upsert, merge, update, or delete operation in Pipelines; Basin Catalog's support for mutable Iceberg tables is a separate capability. [Pipeline SQL](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-pipelines/sql-reference/select-statements.mdx), [stateless scope](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-pipelines/platform/pricing.mdx)

## Three different execution contracts

| Product         | Documented role                                    | Mutation boundary                                                                |
| --------------- | -------------------------------------------------- | -------------------------------------------------------------------------------- |
| Basin Pipelines | Continuous stream transformation and sink delivery | Stream-to-sink insertion; row upsert/delete is not documented.                   |
| Basin SQL       | Queries over persisted Iceberg tables              | Read-only; cannot materialize tables or mutate rows.                             |
| Basin Catalog   | Iceberg metadata and transactional commits         | Compatible external writers can mutate tables; capability depends on the engine. |

Pipelines run one or more `INSERT INTO sink SELECT ... FROM stream` statements with projection, expressions, `WHERE`, CTEs, and restricted `UNNEST`. `FROM` resolves a stream, CTE, or subquery; catalog-table reads are not documented as pipeline inputs. Multiple statements support fan-out, without establishing an atomic multi-table business transaction. Catalog sinks produce Parquet and create their namespace/table; they cannot be created for an existing Iceberg table. Published rolling policy is 300 seconds by default and at least 60 seconds.

The inspected sink API has no primary-key, operation-column, upsert-mode, or CDC-envelope mapping. An `operation='delete'` field remains data unless another consumer interprets it. Resource deletion is separate: deleting a pipeline stops flow, deleting a sink stops writes, and deleting a stream permanently removes unprocessed buffered events and dependent pipelines.

## Delivery, replay, and changes to definitions

Cloudflare documents exactly-once sink delivery. This does not document deduplication of two producer submissions sharing an application event ID. The Worker binding's `send()` resolves when ingestion is confirmed, before table visibility; schema-invalid events can be accepted and subsequently dropped. Preserve immutable event IDs and source sequence positions, and validate actual retry behavior rather than treating acknowledgement as query visibility. [Sink guarantee](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-pipelines/sinks/index.mdx), [ingestion and schema validation](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-pipelines/streams/writing-to-streams.mdx)

Streams are durable buffers, but inspected docs and SDK do not establish user-controlled historical replay, offsets, a retention window, or reprocessing guarantees when a pipeline is recreated. Stream schemas, pipeline SQL, and sink configurations are immutable after creation. Git promotion must therefore plan replacements and verify cutover/replay instead of assuming in-place edits. The SDK's old pipeline update method belongs to a deprecated resource model; the new model exposes creation/deletion and SQL validation. [Streams](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-pipelines/streams/index.mdx), [schema immutability](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-pipelines/streams/manage-streams.mdx), [pipeline API](https://github.com/cloudflare/cloudflare-typescript/blob/6dbe1fc45b41f102e5edcd3630d6fd3e803552ce/src/resources/pipelines/pipelines.ts#L104), [stream API](https://github.com/cloudflare/cloudflare-typescript/blob/6dbe1fc45b41f102e5edcd3630d6fd3e803552ce/src/resources/pipelines/streams.ts)

## Dagflare and dbt-cloudflare-basin

- **Dagflare:** declare continuous stream-to-sink assets, schemas, transformation SQL, ownership, dependencies, health, visibility, and replacement plans. Scheduling/backfills and finite dbt runs remain separate asset operations.
- **dbt-cloudflare-basin:** pursue a standalone integration with no required Dagflare runtime. Pipeline `INSERT ... SELECT FROM stream` differs from compiled dbt queries over persisted relations, including ordinary incremental append. A custom streaming materialization is a candidate requiring ingestion idempotency and visibility verification, distinct from conventional dbt table/incremental semantics. Ordinary merge, delete+insert, snapshots, and full-refresh replacement are not established by this path. Evaluate existing upstream dbt v2/DuckDB integration before implementing an adapter. [Existing-work assessment](dbt-basin-existing-work.md)

An append-only change log can support a **proposed logical current-state query**: ingest full-row create/update events plus tombstones, rank by a strict source sequence for each key, select the latest event, then exclude tombstones. Local DuckDB checks covered duplicate replay, out-of-order updates, deletion, and recreation; filtering deletes before ranking incorrectly resurrected an older row. This is a local logic demonstration, not a Basin-account result.

Stable event IDs, bootstrap completeness, duplicate consistency, and source ordering are required; reject conflicting changes at the same source version. Partial updates need reconciliation. Retain tombstones and replay watermarks to prevent resurrection. Basin SQL documents CTEs and `ROW_NUMBER`, but windows are budget-gated and performance is untested here. Logical exclusion does not remove historical source data. [SQL capabilities and window budgets](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-sql/reference/limitations-best-practices.mdx), [ranking functions](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-sql/sql-reference/index.mdx#L638)

Basin SQL is read-only. Actual row mutations need a write-capable Iceberg engine committing through Catalog. Cloudflare documents Spark row deletion and the distinction between logical deletion and later snapshot/file cleanup. Do not delete table files directly. [Read-only SQL](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-sql/reference/limitations-best-practices.mdx), [transactional row deletion](https://github.com/cloudflare/cloudflare-docs/blob/f00bec2e4a282dce209c83ce5ad43001706ee2fb/src/content/docs/basin-catalog/deleting-data.mdx)

This investigation inspected documentation/API source and checked proposed query logic locally. It did not submit unsupported statements to a live pipeline or validate live ingestion, replay, deduplication, mutations, or current-state queries.
