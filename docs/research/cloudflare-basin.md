# Cloudflare Basin capability assessment

Evidence date: October 13, 2026. References point to the [primary-source register](sources.md). Statements about product support are documentation findings; deployment choices are Dagflare recommendations.

## Platform identity and existing interface

Basin is Cloudflare's serverless analytics platform combining ingestion, table management, and distributed SQL over Apache Iceberg tables in R2. The current docs explicitly rename Cloudflare Data Platform and its three components. Basin Pipelines, Basin Catalog, and Basin SQL are documented as generally available. Existing configurations continue to work, but Catalog and SQL documentation warns that old APIs will eventually be deprecated. Metric datasets still use some R2 Data Catalog names. Avoid hard-coding the assumption that display names, API identifiers, and Wrangler command groups evolve together. [CF01–CF04, CF18](sources.md)

Cloudflare already offers pipeline creation wizards, stream settings, catalog exploration, maintenance configuration and history, query commands, and operational charts. Its primitives are not UI-free. The unmet opportunity is an integrated model of assets, dependencies, runs, contracts, release history, and team operations spanning these services. [CF06, CF11, CF13, CF17, CF18](sources.md)

## Ingestion: streams, transforms, and sinks

The resource model is `stream → SQL pipeline → sink`. A stream is durable buffered ingestion that can feed multiple pipelines. Inputs are JSON through HTTP or Workers bindings. A Worker binding targets the stream ID and exposes `send(records)`, whose promise resolves when records are confirmed ingested. New binding configuration uses `stream`; legacy `pipeline` remains supported with a warning. Schema-specific types can be generated by Wrangler when authenticated. [CF05–CF08](sources.md)

Structured streams define fields and types; unstructured streams expose a JSON `value` column. Current types include strings, integer and floating-point numbers, booleans, timestamps, binary, JSON, lists, and structs. Stream schemas cannot be modified after creation. Crucially, the management guide says events that fail the schema can still be accepted at ingestion and then dropped during processing. User-error metrics describe missing fields, type mismatches, parse failures, and null values. Dagflare must report these processing failures and should support optional validation or quarantine before ingestion when raw-event retention matters. [CF06, CF17](sources.md)

Pipeline SQL filters, reshapes, casts, and computes on events. It supports CTEs and a restricted UNNEST form. Multiple `INSERT INTO sink SELECT ... FROM stream` statements can route one stream into several sinks. Pricing explicitly describes current transforms as stateless and treats future aggregations, joins, and windows separately. Do not infer batch warehouse SQL support from the marketing term “transform.” [CF09, CF10, CF19](sources.md)

Sinks write JSON or Parquet files to R2, or Parquet-backed Iceberg tables through Basin Catalog. A Catalog sink creates the namespace and table, but cannot currently be created for an existing Iceberg table. It requires catalog/storage write credentials. File rolling trades latency for file size: the documented default interval is 300 seconds and the minimum Catalog interval is 60 seconds. Lower latency increases file count and maintenance pressure. [CF12](sources.md)

The Pipelines overview describes exactly-once delivery to R2. This does not establish exactly-once behavior across arbitrary producer retries, Dagflare's queue, a dbt runner, or a multi-asset transaction. Persist upstream event identities and use idempotent orchestration; scope any guarantee to the component whose contract provides it. [CF05, CF26](sources.md)

Cloudflare Logpush provides a native source. The documented datasets are HTTP requests, firewall events, DNS logs, and Workers trace events; availability and underlying Logpush entitlements still depend on the team's account. The setup can automatically create a stream, sink, and pipeline. There is no evidence here of a universal SaaS connector library, general CDC engine, or arbitrary database replication service built into Basin. [CF20](sources.md)

### Implications for resource management

- Treat schema changes as migrations: create replacement resources, validate, switch producers, drain the previous stream, and retain rollback evidence. Never make deletion the default reconciliation action.
- Import existing resources as observed assets before granting Dagflare management authority.
- Keep continuous streaming resources separate from finite materialization runs. A running pipeline is not itself a completed data asset.
- Account for eventual table visibility after file rolling. Display accepted records, dropped records, committed snapshots, and observed table freshness separately.
- Confirm replay/retention and replacement-sink APIs before promising historical replays or zero-loss cutovers. They were not established by the inspected guides.

## Storage and catalog: R2 plus Apache Iceberg

Basin Catalog exposes a standard Iceberg REST catalog attached to an R2 bucket. It tracks table metadata and supports compatible engines including Spark, Trino, DuckDB, Snowflake, and PyIceberg. Iceberg supplies the open table format, metadata evolution, and commit/snapshot model; engine-specific support still matters. R2 data access has no egress fee, but storage and operation charges apply. [CF03, CF11, CF21, CF22](sources.md)

Cloudflare documents automated compaction and snapshot expiration. Compaction combines small Parquet files; the documented target size range is 64–512 MB, with 128 MB as the configuration default. Snapshot expiration uses an age threshold plus a minimum snapshot count. These operations have catalog/table controls and maintenance history in the dashboard. Orphaned files that were never referenced by snapshots are not removed by the documented maintenance feature. [CF11, CF13](sources.md)

Code releases and Iceberg snapshots are different versions. A Git commit changes the transformation definition; an Iceberg snapshot records table state. Maintenance can rewrite physical files and produce snapshots without a business-data change. A rollback of a Worker or Git definition does not roll back Iceberg data. Dagflare should record both versions and classify maintenance observations separately from semantic data materializations.

### Authentication and locality

Catalog authentication requires both catalog and underlying R2 storage permissions. The catalog vends SigV4 credentials whose storage rights inherit the authenticating token. A token that has catalog read-only rights but R2 write rights can still modify underlying objects. A genuinely read-only role must constrain both scopes, and application authorization must also prevent direct writes through its service credentials. [CF11](sources.md)

The current Catalog management guide explicitly says non-default R2 jurisdictions are unsupported. Location hints and default-jurisdiction deployment do not establish a legally enforced EU data boundary. A jurisdiction requirement is an adoption gate, not a UI feature to postpone. [CF11](sources.md)

## Querying and serving: Basin SQL

Basin SQL is a distributed analytical query engine over Catalog-managed Iceberg tables. It is not a writable database. The retrieved support matrix includes SELECT, filters, grouping, aggregates, CTEs, standard joins, several subquery forms, inline window functions, QUALIFY, set operations, and EXPLAIN. Large distinct aggregates, windows, and joins have memory and scan-related constraints; some functions are budget-gated before execution. [CF14–CF16](sources.md)

Important unsupported features include INSERT/UPDATE/DELETE, CREATE/DROP/ALTER, OFFSET, UNNEST, PIVOT, named WINDOW clauses, and lateral derived tables. Pipeline SQL and Basin SQL are different dialects: Pipeline UNNEST support does not imply query-engine UNNEST support. A SQL editor must select a dialect and validate against that engine's capabilities. [CF10, CF16](sources.md)

Queries can use Wrangler or HTTP. The docs show the Basin SQL endpoint on `api.sql.cloudflarestorage.com`, and Wrangler reads `WRANGLER_BASIN_SQL_AUTH_TOKEN`. The management plane and SQL/data endpoints are separate destinations; allowlisting only `api.cloudflare.com` is insufficient. The query-auth guide includes R2 admin/write scopes, whereas the Catalog guide discusses fully read-only storage access. Determine the actual least-privilege token that works in an account-level test before shipping permission presets. [CF15, CF11](sources.md)

For the UI, provide bounded previews, explicit query execution, scan statistics when returned, and filters that reduce scanned data. Do not automatically execute a full-table count or fetch a new sample whenever a user navigates. OFFSET pagination is unavailable; a stable key-based approach or bounded result cache is a design task, not an assumed database feature.

Serving data through a Worker can provide authorization, result shaping, caching, and a domain API. This does not turn a lakehouse query into a low-latency transactional database. Store Dagflare's mutable operational metadata in D1 or Durable Objects, and benchmark query performance before committing to external serving SLAs.

## dbt and general transformation execution

dbt table and incremental materializations require writes, DDL, and adapter-specific behavior. Basin SQL cannot provide those operations. No official native Basin dbt adapter was established in this research.

Cloudflare's DuckDB example requires version 1.4+ and demonstrates attaching the Iceberg catalog and creating a table. It also notes DELETE limitations on partitioned tables. The dbt-duckdb adapter exposes extension loading, secrets, attached catalogs, and arbitrary ATTACH options. Together these interfaces suggest a feasible runner, but do not prove that dbt's temporary tables, rename/swap operations, incremental strategies, tests, and retries work against Basin. [CF21, DB01](sources.md)

Recommended proof: a Cloudflare Container runs a pinned Python/dbt/DuckDB environment, authenticates to Basin Catalog, executes a small project, uploads manifest/run-result/log artifacts to team-owned R2, and returns snapshot evidence to Dagflare. First prove this with a live account, then containerize and measure it. Spark/Trino or a team-controlled external runner remain fallback adapters if required semantics exceed DuckDB's supported operations. Avoid inventing a Basin adapter before checking the existing path.

PyIceberg is a documented client for creating and inspecting tables. It is useful for metadata checks and targeted writes, but is not itself a dbt SQL engine. [CF22](sources.md)

## Supporting Cloudflare primitives

| Primitive                           | Appropriate Dagflare use                                                          | Boundary                                                                                                         |
| ----------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Workers and static assets           | Browser application, API, webhooks, authorization, lightweight adapter calls      | Runtime CPU/memory limits; not a general Python warehouse process                                                |
| Workflows                           | Durable run steps, bounded retries, waiting for callbacks, execution coordination | Does not supply an asset catalog, partition semantics, or exactly-once external side effects                     |
| D1                                  | Definitions index, asset projections, run/event index, roles, audit records       | Paid maximum 10 GB per database; archive bulky logs and artifacts to R2                                          |
| Durable Objects                     | Serialized admission, leases, scheduler coordination, live subscriptions          | State must be durable; process memory does not survive eviction/deployment                                       |
| Queues                              | Asynchronous work/events and dead-letter handling                                 | At-least-once delivery; deduplicate and handle out-of-order events                                               |
| Cloudflare Access                   | Team identity and an authentication boundary                                      | Worker must validate JWTs; app RBAC and Git permissions remain separate                                          |
| Containers                          | Python/dbt and other processes requiring a conventional runtime                   | Local development needs Docker; deployment limits, image lifecycle, credentials, and persistence need validation |
| K2                                  | Optional retained event-log/replay adapter                                        | Public beta, documented beta storage quota; not required for the first version                                   |
| Analytics SQL binding               | Optional account analytics queries from Workers                                   | A separate analytics service; do not assume it queries Basin tables                                              |
| Hyperdrive / Workers AI / Vectorize | Potential future source or AI integrations                                        | Not prerequisites for the chosen Basin asset workflow                                                            |

Sources: [CF23–CF34](sources.md). Cloudflare's current Containers docs include a beta Durable Object scheduling policy with runtime-selected images and filesystem snapshots. Snapshot support is policy-specific, image-bound, and has a retention limit; it is not a general durable database or code/data rollback system. Prefer the simpler default policy unless runtime-selected images are necessary. [CF28–CF30](sources.md)

Workflows can be triggered through bindings/API or scheduled directly through a binding's `schedules` field. Current docs allow up to 100 Workflow schedule expressions per account and identify a dedicated cron concurrency budget. Worker Cron Triggers use UTC, and configuration changes can take up to 15 minutes to propagate. Dynamic team schedules and timezone semantics therefore need a Dagflare scheduler design; one deployed cron per asset is not a scalable universal solution. [CF23–CF25](sources.md)

Workflow non-stream step results and event payloads are limited to 1 MiB. Paid default steps are 10,000, configurable to 25,000. Paid state/log retention is documented as 30 days, so long-term run evidence belongs in Dagflare storage. The limits page's table and explanatory prose disagree on an active-instance concurrency number; treat account quotas as discoverable configuration, not a fixed design assumption. [CF24](sources.md)

## Current quotas and economic model

The Pipeline limits page currently lists 20 streams, 20 sinks, and 20 pipelines per account; 5 MB per ingestion request; and a maximum ingest rate of 1 GB/s per stream. These are published limits, not measured service guarantees. Preview provisioning must budget capacity across the whole account, including resources Dagflare does not own. [CF07](sources.md)

| Cost dimension              | Retrieved pricing snapshot                                 | Product implication                                      |
| --------------------------- | ---------------------------------------------------------- | -------------------------------------------------------- |
| Stream ingress              | Free; subject to service limits                            | Free ingress does not mean free pipeline execution       |
| Stateless SQL transforms    | 50 GB/month included, then $0.04/GB                        | Filter volume and resource fan-out affect cost           |
| JSON sink output            | After included sink usage, $0.03/GB                        | Meter uncompressed output                                |
| Parquet/Iceberg sink output | After included sink usage, $0.06/GB                        | Each sink contributes output volume                      |
| Catalog operations          | 1 million/month included, then $9/million                  | Polling and metadata exploration consume requests        |
| Compaction bytes            | 10 GB/month included, then $0.005/GB                       | Small-file strategy affects maintenance cost             |
| Compaction objects          | 1 million/month included, then $2/million                  | Show file counts as well as byte counts                  |
| Basin SQL scans             | 10 GB/month included, then $0.0025/GB; 10 MB/query minimum | Frequent previews are not cost-free                      |
| R2 Standard storage         | $0.015/GB-month before applicable allowances               | Include data, artifacts, history, and retained snapshots |

Sources: [CF19, CF35, CF36, CF37](sources.md). Storage and operation fees, Workers Paid subscription, D1, Workflows, Containers, identity products, and external runners are additional dimensions. Allowances are account-level and shared with other workloads; Dagflare cannot assign the full allowance independently to every project.

A useful estimator accepts input bytes, transform bytes, each sink's uncompressed bytes, stored bytes, compaction bytes/object count, catalog operations, scan volume, and runner duration. It should show estimates separately from observed usage. This is more honest than claiming “zero-cost orchestration” because the data plane is serverless.

## Capability gaps Dagflare must own

The inspected Basin guides do not establish a unified cross-resource asset DAG, dependency-aware batch scheduler, partition-aware backfill planner, integrated dbt lifecycle, Git-reviewed definition promotion, app-level team roles, or end-to-end business-data lineage. These are proposed Dagflare capabilities, not hidden Basin features assumed to exist.

The critical unanswered questions concern live API coverage for catalog discovery and maintenance, safe stream migration/replay, query credentials and cancellation, schema evolution across writers, dbt materialization compatibility, runner isolation, and account portability. The [validation plan](../design/validation-plan.md) turns each into a concrete experiment and adoption gate.
